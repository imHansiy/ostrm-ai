# 分阶段流水线验证记录

验证日期：2026-11-18，北京时间。部署环境为 Serv00 FreeBSD、远程 TiDB、在线 MiniCPM-V；没有使用本地模型或 Docker。

## 实现与资源约束

- 默认一个视频准备槽位、一个模型槽位，允许两个视频处于活动状态；准备与模型可以重叠，不同时启动两次整片压缩。
- 保留完整视频压缩、字幕提取、模型输入和提示词。部署时对 `media.py`、`model.py`、`subtitles.py` 与上一版本逐字节比较一致。
- 封面与协议发布转入持久化 `postprocess_jobs`，与成功结果在同一数据库事务中提交；上传失败保留本地封面，并继续发布协议资料。
- 取消在模型槽位获得后强制复查，保存前再次检查取消与文件版本。准备好的任务在意外重启后重新入队，并按原证据缓存策略复用压缩内容。

- Python 完整回归：122 项通过。涵盖真实 FFmpeg、OCR 数据流、SQLite 备份、API 权限及已有协议功能。

“各自耗时之和”是同批真实任务的顺序执行参考值，并非将同一文件在旧版重新识别的 A/B 测试；后两组共享一个任务，不能当作独立样本累加。结果证明消除了部分串行等待，不能据此承诺全库固定提速比例。

升级前最近 20 条成功记录平均完成间隔为 50 秒，文件时长中位数 15.9 秒；升级后批次混有 1 GiB 游戏录像、损坏文件及失效路径，直接比较整批均速会混入文件差异和失败等待，不作为提速结论。

## 仍然存在的限制

- 部分 OneDrive 目录封面上传返回 403。私有封面缓存和协议发布不受阻塞，同目录封面任务保留并退避重试；本次没有修改网盘权限。
- 原中间文件大小上限、损坏/失效视频、上游读取失败仍可能使任务失败。流水线不跳过完整时间线校验，也不会把失败视频当作识别成功。
- 百度下载出口问题继续暂缓，成功结果不重复识别。

各部署会因源文件、网络、模型响应、共享主机负载而不同。新的 `performance` 历史按任务记录证据准备、等待模型槽位及模型与保存耗时，便于后续持续分析。
